# API для владельца магазина

Один справочник по эндпоинтам приложения владельца магазина (роль `shop_owner`). Базовый префикс: `/api/v1`. Все запросы с заголовком `Authorization: Bearer <token>`. Доступ к `/shop/*` и `/pos/*` имеют только пользователи с ролью `admin` или `shop_owner`.

**Несколько магазинов на одного владельца:** у одного аккаунта `shop_owner` может быть несколько записей в таблице магазинов. Список: `GET /shop/stores` (в каждой записи при необходимости: `localApiDataReceivedAt`, `lastNetworkStockAt` — последний пинг локального API в облако и последняя выгрузка пакета остатков сети). Добавить точку (после входа): `POST /shop/stores` (тело как при регистрации магазина: `shopName`, `inn`, `certificate`, `certificatePhotoUrl`, опционально `description`, `address`, `cityId`, `logo`, `phone`, `email`). Для запросов к «текущей» точке передайте заголовок **`X-Shop-Id: <uuid>`** (или query `?shopId=`). Если заголовок не указан, используется первая точка по `sort_order`, `created_at`. Без контекста магазина: список заказов и каталог в кабинете агрегируются по **всем** точкам владельца; снимки POS, `GET /shop/me`, лимиты Cloudinary — по выбранной точке.

## Авторизация

Вход общий с клиентом:

| Метод | Путь | Тело | Ответ |
|-------|------|------|--------|
| POST | `/auth/login` | `{ "phone": "string", "password": "string" }` | `{ success, data: { user, token, refreshToken } }`. У пользователя `user.role.name` = `shop_owner` или `admin`. |

Дальше во всех запросах подставляйте заголовок: **`Authorization: Bearer <token>`**.

## Товары (своего магазина)

| Метод | Путь | Тело / Query | Ответ |
|-------|------|----------------|--------|
| GET | `/shop/products/` | query: `category`, `gender`, `search`, `sort_by`, `sort_order`, `page`, `limit` | `{ success, data: { products[], total, page, limit } }` |
| GET | `/shop/products/:id` | — | один товар (ProductResponse) |
| POST | `/shop/products/` | см. ниже | созданный товар |
| PUT | `/shop/products/:id` | то же тело, что при создании | обновлённый товар |
| PATCH | `/shop/products/:id/sort-order` | `{ "sortOrder": number }` | обновлённая сортировка |
| DELETE | `/shop/products/:id` | — | удаление товара |

**Тело создания/обновления товара (POST/PUT):**
```json
{
  "name": "string",
  "description": "string",
  "gender": "male | female | unisex",
  "categoryId": "uuid",
  "brand": "string",
  "sortOrder": 0,
  "variations": [
    {
      "sizeIds": [1, 2],
      "colorIds": [1, 2],
      "price": 0,
      "originalPrice": 0,
      "discount": 0,
      "imageUrls": [],
      "imageUrlsByColor": {},
      "stockQuantity": 0,
      "sku": "",
      "barcode": ""
    }
  ]
}
```
Фото загружаются отдельно: `POST /upload/image`, в товар подставляются только URL из ответа сервера.

## Заказы — логика для владельца магазина

Владелец видит только заказы, в которых есть **позиции его магазина**. По каждому заказу он управляет **только своими позициями** (подтвердить, отклонить, отметить возврат). Общий статус заказа (готовится, в доставке, доставлен) выставляет **админ**.

### Что видит владелец

- **Только заказы с позициями своего магазина.** В одном заказе могут быть и свои, и чужие позиции — различие по `shop_id` у позиции (свои — где `shop_id` совпадает с вашим магазином).
- **Список заказов:** заказы, в которых есть хотя бы одна позиция вашего магазина.
- **Один заказ:** полный заказ с разбивкой по магазинам; по `shop_id` или по полю `shop` у позиции можно отфильтровать «свои» строки.

### Действия по своим позициям

Один эндпоинт для смены статуса **только по позициям вашего магазина** в заказе:

**PUT** `/shop/orders/:id/status`

**Тело (одно из):**
```json
{ "status": "confirmed" }
```
```json
{ "status": "rejected" }
```
```json
{ "status": "returned" }
```

| status | Значение |
|--------|----------|
| **confirmed** | Свои позиции подтверждены (готовы к отгрузке). |
| **rejected** | Свои позиции отклонены (не выполняете). |
| **returned** | По своим позициям отмечен возврат (клиент вернул товар / возврат принят). |

Обновляются только позиции вашего магазина; общий статус заказа пересчитывается автоматически по всем магазинам.

### Кто выставляет доставку

Статусы **«Готовится»**, **«В доставке»**, **«Доставлен»**, **«Завершён»** выставляет **админ** (через админку или `PUT /api/v1/admin/orders/:id/status`). Владелец магазина эти статусы не меняет.

Типичный сценарий:

1. Владелец подтверждает свои позиции: `PUT /shop/orders/:id/status` с телом `{ "status": "confirmed" }`.
2. Админ выставляет заказу статус **inDelivery** (в доставке).
3. После доставки клиенту админ выставляет **delivered** или **completed**.

### Оплата получена

Когда оплата по заказу получена (нал/карта), владелец может отметить это по заказам, где есть его товары:

**POST** `/shop/orders/:id/payment-received`

Без тела. После вызова в заказе заполняются `payment_received_at` и `payment_status` = `paid`; **клиенту становится доступен чек**.

## POS: остатки и продажи

Префикс можно использовать **`/shop/pos`** или **`/pos`** (одна и та же логика).

| Метод | Путь | Тело / Query | Ответ |
|-------|------|----------------|--------|
| GET | `/shop/pos/products/stock` или `/pos/products/stock` | query: `in_stock` (опционально, напр. `true`) | список вариаций с остатками (variationId, productId, productName, sku, stockQuantity, isAvailable и т.д.) |
| PUT | `/shop/pos/products/:variationId/stock` или `/pos/products/:variationId/stock` | `{ "stockQuantity": number }` (≥ 0) | `{ variationId, oldQuantity, newQuantity }` |
| POST | `/shop/pos/products/bulk-upload` или `/pos/products/bulk-upload` | массив товаров с вариациями (name, categoryId, gender, variations с price, stockQuantity, sizes, colors и т.д.) | результат массовой загрузки |
| POST | `/shop/pos/sales/sync` или `/pos/sales/sync` | `{ "sales": [ { "variationId", "quantity", "size", "color", "price", "saleDate" } ] }` | списание со склада по продажам, ответ с обработанными/ошибками |

## Сеть магазинов (остатки по глобальным вариациям в облаке)

Свод по строкам `shop_global_stock_lines`, принятым с локальных POS (лицензия + `shop-stock-lines-receipt`). Данные **по всем точкам** владельца; для UI кабинета запрос без привязки к одной точке (заголовок `X-Shop-Id` на ответ не влияет).

| Метод | Путь | Query | Ответ |
|-------|------|--------|--------|
| GET | `/shop/network-stock-summary` | опционально `limit` (1…10000, по умолчанию 2000) | `{ success, data: { rows: [ { shopId, shopName, globalVariationId, globalProductId?, qty, receivedAt } ], count, limit } }` |

Для ролей `admin` / `super_admin` требуется query **`ownerUserId`** (UUID пользователя-владельца).

## Регистрация/обновление клиента магазина (POS, бонусы)

Публичный эндпоинт (проверка по `shopId`). Используется программой магазина для регистрации клиента и бонусов.

| Метод | Путь | Тело | Ответ |
|-------|------|------|--------|
| POST | `/shop/customers/register` | `{ "shopId": "uuid", "phone": "string", "qrCode": "string?" (обязателен при первой регистрации), "bonusAmount": number }` | клиент / обновлённые бонусы |

---

## Формат ответов

- Успех: `{ "success": true, "data": ... , "message"?: "string" }`.
- Ошибка: `{ "success": false, "error": { "code": "string", "message": "string" } }`.

В ответе заказа у каждой позиции есть `shop_id` и при необходимости `shop` — по ним приложение владельца отбирает «свои» позиции и отображает только их или помечает их в общем списке.
