# UI/UX гайд для экрана "Добавление товара" (POS)

Документ описывает, как устроен текущий UX в `pos.libiss.com`, чтобы в другом приложении реализовать похожий сценарий без потери логики и удобства.

---

## 1) Цель экрана

Экран добавления товара должен:

- быстро провести пользователя по шагам от базовых полей до отправки;
- минимизировать ошибки при выборе цветов/размеров и заполнении вариаций;
- дать понятный предпросмотр перед сохранением;
- стабильно работать на мобильных устройствах (камера, фото, ввод чисел).

---

## 2) Общая UX-модель

Используется мастер из 5 шагов:

1. Основная информация
2. Цвета и размеры
3. Вариации
4. Фото по цветам
5. Проверка перед отправкой

### Почему именно мастер

- Пользователь решает одну подзадачу за раз.
- Снижается когнитивная нагрузка.
- Ошибки находятся на раннем шаге, а не в конце.
- Легче поддерживать мобильный UX (меньше полей одновременно).

---

## 3) Информационная архитектура экрана

Экран делится на 4 зоны:

- **Header**: заголовок, краткая подсказка, индикатор шага.
- **Body**: поля текущего шага.
- **Inline help**: текстовые подсказки, ограничения, сообщения валидации.
- **Footer actions**: кнопки `Назад`, `Далее`, `Сохранить`.

### Принципы размещения

- Важные поля сверху (название, категория, пол, цена).
- Зависимые поля ниже (размеры зависят от типа размера).
- Неблокирующие детали (бренд, сезон, QR) не перегружают первый экран.

---

## 4) Поведение по шагам

## Шаг 0: Основные данные

Поля:

- `name` (обязательно)
- `description` (опционально)
- `gender` (обязательно: `male | female | unisex`)
- `categoryId` (обязательно, через селектор категорий)
- `seasonId` (опционально)
- `price` (обязательно)
- `discount` (опционально, 0-100)
- `qrCodeUrl` (опционально, readonly если заполняется сканером)

UX-правила:

- Ошибка показывается под полем сразу при попытке перейти дальше.
- Для скидки показывается вычисление итоговой цены.
- Категория выбирается через отдельный понятный контрол (не сырое поле UUID).

## Шаг 1: Цвета и размеры

Элементы:

- список цветов (чекбоксы, с визуальным hex);
- выбор типа размера;
- список размеров под выбранный тип.

UX-правила:

- Обязательно минимум 1 цвет и 1 размер.
- Переключение типа размера обновляет список размеров.
- Состояние выбранных пунктов визуально явное (active/check).

## Шаг 2: Вариации

Логика:

- создается декартово произведение `цвет × размер`;
- для каждой строки: цена, остаток, скидка, QR (опционально).

UX-правила:

- Автозаполнение цены из базовой.
- По умолчанию остаток > 0 (например 1), чтобы пользователь не создавал "пустые" товары.
- Таблица/карточки вариаций должны быть легко сканируемы.

## Шаг 3: Фото по цветам

Логика:

- фото прикрепляются к конкретному цвету;
- лимит фото на цвет (например 5);
- источники: камера + галерея.

UX-правила:

- Превью сразу после выбора.
- Возможность удалить конкретное фото.
- Явный счетчик: `N/5`.

## Шаг 4: Проверка

Показываем итог:

- ключевые поля товара;
- список вариаций;
- фото по цветам;
- режим загрузки фото (например compressed/original).

UX-правила:

- На этом шаге ничего не "угадывается": пользователь видит именно то, что будет отправлено.
- Кнопка отправки блокируется на время загрузки.
- После успеха: понятный success-state и возврат в список товаров.

---

## 5) Состояния интерфейса (states)

Нужно явно реализовать 6 состояний:

1. **Loading**: загрузка справочников и/или товара для редактирования.
2. **Ready**: форма активна.
3. **Dirty draft**: есть несохраненные изменения.
4. **Submitting**: загрузка фото + отправка товара (кнопка disabled).
5. **Success**: товар успешно создан/обновлен.
6. **Error**: ошибка запроса или валидации.

### UX-паттерны для состояний

- Не скрывать контекст при ошибке: пользователь должен остаться на шаге и исправить.
- Для сетевых ошибок показывать human-readable текст + техническую причину в detail (если нужно).
- Для долгих операций использовать прогресс/спиннер и запрет повторного клика.

---

## 6) Валидация и сообщения

### Правила валидации (минимум)

- `name` обязательно;
- `gender` обязательно;
- `categoryId` обязательно;
- минимум 1 цвет;
- минимум 1 размер;
- минимум 1 вариация;
- `price > 0`;
- `stockQuantity >= 0`;
- `discount` в диапазоне 0..100.

### Тексты ошибок (рекомендуемый стиль)

- Коротко и предметно: "Выберите хотя бы один цвет".
- Без технического жаргона для бизнес-пользователя.
- Для API ошибок можно дать вторую строку с причиной.

---

## 7) Работа с черновиком

Рекомендуется автосохранение draft в local storage:

- на `Next`;
- при изменении вариаций;
- при изменении фото.

Что хранить:

- текущий шаг;
- значения полей формы;
- выбранные id цветов и размеров;
- массив вариаций.

UX-правила:

- При повторном входе предлагать восстановление.
- После успешной отправки очищать draft.

---

## 8) Мобильный UX

Обязательные требования:

- кликабельные зоны не меньше 40px;
- цифровая клавиатура для цен/остатка;
- камера через `capture=environment`;
- фото и таблицы не должны ломать верстку на узких экранах;
- кнопка действия всегда доступна (липкий footer или понятный скролл).

---

## 9) Доступность (a11y)

Минимум:

- `label` для каждого поля;
- понятные `aria` атрибуты для интерактивных элементов;
- контраст текста и ошибок;
- фокус-стили для клавиатурной навигации.

---

## 10) Визуальный стиль (дизайн-система)

Рекомендации для единообразия:

- единая шкала отступов (например 4/8/12/16/24);
- единые радиусы и тени карточек;
- один компонент кнопки для primary/secondary/destructive;
- единый стиль инпутов и сообщений валидации;
- чипы/бейджи для цвета и размера.

---

## 11) API-aware UX (важно для интеграции)

Интерфейс должен быть синхронизирован с серверной моделью:

- для отправки использовать `sizeIds` и `colorIds`, а не текстовые названия;
- фото сначала грузятся отдельным endpoint, в товар отправляются URL;
- итоговый payload формируется только после успешного получения URL картинок;
- при 401 пробовать refresh (если реализовано), иначе отправлять на login.

---

## 12) Рекомендованный пользовательский сценарий

1. Пользователь открывает экран "Добавить товар".
2. Система загружает справочники.
3. Пользователь заполняет шаг 0.
4. Выбирает цвета/размеры.
5. Система генерирует вариации.
6. Пользователь корректирует цену/остатки по вариациям.
7. Загружает фото по цветам.
8. Проверяет итоговый экран.
9. Нажимает "Сохранить".
10. Система загружает фото, затем отправляет payload товара.
11. Показывается успех и переход в список.

---

## 13) Чеклист готовности UI/UX

- [ ] Все 5 шагов реализованы и связаны одной навигацией.
- [ ] Валидация работает до отправки.
- [ ] Есть понятные ошибки по шагам.
- [ ] Реализована загрузка фото по цветам.
- [ ] Есть предпросмотр итоговых данных.
- [ ] Draft сохраняется и очищается после успеха.
- [ ] Есть состояния loading/submitting/success/error.
- [ ] Мобильная версия проверена.
- [ ] Payload соответствует API (`sizeIds`, `colorIds`, `imageUrlsByColor`).

---

## 14) Что можно улучшить в следующей версии

- Массовое редактирование вариаций (цена/остаток "применить ко всем").
- Автопредложение SKU/Barcode шаблонов.
- Более явный прогресс загрузки фото по каждому цвету.
- Undo после удаления фото.
- Шаблоны товаров для быстрого создания похожих карточек.

Базовый префикс: `/api/v1`

**Request:**

