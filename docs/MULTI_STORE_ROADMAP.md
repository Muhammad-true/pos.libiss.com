# Roadmap: 1 владелец и несколько магазинов

Документ фиксирует поэтапный план внедрения сценария:

- один владелец;
- несколько магазинов (сейчас 3, в будущем больше);
- остатки по каждой точке;
- перемещения между магазинами;
- совместимость со старыми клиентами без поломок.

---

## 1) Бизнес-цель

Сделать работу сети магазинов в единой системе:

- кассир на точке видит остаток своей точки;
- если нужного размера нет, видит наличие в других магазинах владельца;
- отправляет запрос на перемещение;
- после подтверждения товар перемещается и становится доступен к продаже.

---

## 2) Принцип "не ломаем старых"

Внедрение только через обратную совместимость:

- старые API и старый поток продаж остаются;
- новый функционал вводится в `v2` эндпоинтах;
- переключение владельцев по feature-flag;
- по умолчанию старые клиенты работают как раньше.

### 2.1 Режимы работы

- `single_store_mode` (legacy): текущая логика без разделения остатков по точкам.
- `multi_store_mode`: остатки и продажи с учетом конкретного магазина.

### 2.2 Feature flags

Рекомендуемые флаги:

- `ff_multi_store_enabled`
- `ff_store_transfer_enabled`
- `ff_store_visibility_cross_stock`
- `ff_dual_write_inventory`

---

## 3) Целевая архитектура

### 3.1 Глобальный сервер (`api.libiss.com_global/api`)

Отвечает за:

- владельца и его магазины;
- тариф и лимит количества магазинов;
- лицензирование магазина;
- выдачу токенов и прав.

### 3.2 Локальный сервер (`libiss_local_serverApi`)

Отвечает за:

- остатки по точкам;
- продажи с конкретной точки;
- перемещения между точками;
- локальную скорость и оффлайн-устойчивость.

### 3.3 POS приложение (`libiss_pos_app`)

Отвечает за:

- выбор/фиксацию текущего магазина на устройстве;
- показ остатков своей и других точек;
- создание и обработку заявок на перемещение.

### 3.4 Сайт владельца (`pos.libiss.com_site`)

Отвечает за:

- регистрацию владельца;
- создание и настройку магазинов;
- управление лицензиями/слотами магазинов;
- базовый мониторинг статусов точек.

---

## 4) Модель лицензирования (рекомендуемая)

Рекомендуется: **тариф владельца + лимит магазинов**.

Пример:

- тариф "Business 3" -> `maxStores = 3`;
- владелец может открыть 3 активные точки;
- можно расширить план до 5/10 без рефакторинга.

Преимущества:

- удобная продажа подписки;
- гибкое масштабирование;
- прозрачные ограничения по точкам.

---

## 5) Поэтапный план внедрения

## Этап 0. Подготовка (без изменений для клиентов)

Цель:

- утвердить контракт API и схему данных;
- включить только технические флаги (все off).

Результат:

- старые клиенты не замечают изменений.

## Этап 1. Глобальный контур: владелец и магазины

Сделать:

- сущности владельца и магазинов;
- лимит магазинов по тарифу;
- API создания/списка/деактивации магазинов;
- привязка магазина к лицензии/слоту.

Важно:

- текущую схему магазина не ломать;
- старые токены и логин остаются рабочими.

## Этап 2. Локальная БД: остатки по локациям

Сделать новые таблицы:

- `inventory_locations` (`store`, `central_warehouse`);
- `inventory_balances` (остаток по `location_id + variation_id`);
- `inventory_transfers`;
- `inventory_transfer_items`;
- `inventory_transfer_events` (аудит).

Сделать миграцию:

- создать legacy-локацию;
- перенести текущие остатки в новую таблицу;
- включить `dual-write` (временно писать и в старую, и в новую модель).

Важно:

- старые поля `products.stock` и `product_variations.stock` пока не удалять.

## Этап 3. API v2 для перемещений

Добавить:

- просмотр остатков по всем магазинам владельца;
- создание запроса перемещения;
- подтверждение/отклонение источником;
- приемка получателем;
- журнал перемещений.

Состояния перемещения:

- `requested` -> `approved` -> `in_transit` -> `received`
- альтернативы: `rejected`, `cancelled`.

## Этап 4. POS UI (мягкий запуск)

Сделать:

- отображение "остаток на моей точке";
- блок "есть в других магазинах";
- кнопка "Запросить перемещение".

Пока без жесткого запрета продажи:

- если флаг выключен, касса работает по legacy-логике.

## Этап 5. POS UI (боевой режим)

Сделать:

- продажа только из остатка текущего магазина;
- приемка перемещений в интерфейсе магазина;
- уведомления о заявках (источник/получатель).

Включение:

- только для владельцев, прошедших миграцию и пилот.

## Этап 6. Стабилизация и завершение

Сделать:

- сверки остатков (legacy vs v2);
- метрики и алерты;
- отключение `dual-write` после стабилизации;
- оставить legacy read-only на переходный период.

---

## 6) Изменения для `pos.libiss.com_site` (регистрация и открытие магазинов)

Нужно реализовать пользовательский поток на сайте:

1. Владелец регистрируется/входит.
2. Видит свой тариф и лимит магазинов (`maxStores`).
3. Создает магазины: название, адрес, телефон, timezone, валюта.
4. Для каждого магазина получает статус:
   - `pending_setup`
   - `active`
   - `inactive`
5. Для магазина получает `store_uuid` и инструкции по подключению POS.
6. Видит список магазинов и статус лицензии по каждой точке.

### 6.1 Минимальные страницы сайта

- `Owner Onboarding`
- `My Stores`
- `Create Store`
- `Store Details`
- `Licenses / Plan`
- `POS Connection Guide`

### 6.2 Минимальные API сайта

- `POST /owner/register`
- `POST /owner/login`
- `GET /owner/stores`
- `POST /owner/stores`
- `PATCH /owner/stores/:id`
- `POST /owner/stores/:id/activate`
- `GET /owner/plan`

Примечание:

- конкретные пути можно адаптировать под текущий нейминг `/api/v1/shop/*`.

---

## 7) Правила бизнеса

- перемещения только между магазинами одного владельца;
- продажа списывает остаток только текущей точки;
- владелец видит остатки и движения всех своих точек;
- кассир видит только доступное по своей роли;
- каждое перемещение имеет автора, подтверждающего и время приемки.

---

## 8) Тест-план (обязательный)

### 8.1 Совместимость

- старый POS + новый backend (все флаги off) -> полностью рабочий поток;
- новый POS + владелец в legacy-режиме -> безопасный fallback.

### 8.2 Функционал multi-store

- в магазине A нет размера;
- система показывает наличие в B/C;
- создается заявка;
- B подтверждает;
- A принимает;
- продажа проходит из A.

### 8.3 Негативные кейсы

- попытка переместить больше остатка;
- источник/получатель другого владельца;
- превышен лимит магазинов;
- магазин без активного слота лицензии.

---

## 9) Rollout-план (без риска)

1. Deploy БД + API без включения флагов.
2. Включить только read-only просмотр кросс-остатков для пилотного владельца.
3. Включить перемещения для пилота.
4. Включить строгую продажу по точке для пилота.
5. Постепенно раскатить на остальных.

Rollback:

- выключить feature flags;
- вернуться в legacy-режим без отката схемы БД.

---

## 10) Definition of Done

Функция считается готовой, когда:

- старые клиенты работают без изменений;
- владелец может создать до `maxStores` магазинов на сайте;
- кассир видит наличие в других магазинах;
- перемещение выполняется end-to-end;
- продажа корректно списывает остаток нужной точки;
- есть аудит и отчеты по движениям.

---

## 11) Рекомендуемый порядок реализации по репозиторию

1. `api.libiss.com_global/api`: owner/store/plan/license API.
2. `libiss_local_serverApi`: inventory v2 + transfers + dual-write.
3. `libiss_pos_app`: UI просмотра остатков и запросов перемещений.
4. `pos.libiss.com_site`: регистрация владельца, открытие магазинов, управление слотами.

Такой порядок минимизирует риск поломки и дает быстрый бизнес-результат.
